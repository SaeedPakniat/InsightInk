## High

### H-01 — Related Ideas are backend-ready but absent from Idea Detail

Evidence:

- Product overview explicitly requires users to “discover related ideas”.
- Frontend design maps the prototype AI/Idea-exploration concept to a non-LLM related/recommended Ideas panel.
- Roadmap Phase 13 explicitly includes Jaccard related Ideas.
- Backend already exposes:
  - `GET /api/v1/ideas/:idea_id/related/`
  - public/AllowAny;
  - deterministic related-Idea score/similarity/reason payload.
- Current frontend has no API wrapper, query, component, or rendering path for that endpoint.
- `IdeaDetailPage` ends with source context + comments and never renders related content.

Impact:

A documented core discovery capability is unavailable even though the backend contract already exists.

Recommendation:

Implement a bounded FE task that:
- adds exact related-Idea API types/client;
- adds a small lazy/lightweight Related Ideas section to Idea Detail;
- reuses IdeaCard where appropriate;
- preserves anonymous/public Idea reading;
- handles loading/error/empty states;
- hydrates engagement only when authenticated;
- keeps reason language/content direction correct;
- adds English/Persian tests and mobile/RTL review.

No architecture escalation is required unless the actual backend response differs from the landed contract.

### H-02 — UI language toggle is not synchronized with account `preferred_ui_language`

Evidence:

- `CurrentUser.preferred_ui_language` exists and `PATCH /api/v1/me/` already supports it.
- Registration persists the current UI language once.
- After registration, `LanguageToggle` calls `changeUiLanguage()`, which changes only:
  - localStorage;
  - document lang/dir;
  - i18next language.
- Login/session startup does not reconcile local UI language with the authenticated account preference.
- Backend recommendation explanations explicitly use `User.preferred_ui_language`.
- `RecommendedIdea` displays that backend-generated explanation as returned.

Impact:

After a user changes UI language:
- the current tab changes correctly;
- the server account preference remains stale;
- recommendation explanation language may disagree with the visible UI;
- another device/browser does not inherit the user's account language preference.

This violates the project's separation-and-persistence model for `preferred_ui_language`.

Recommendation:

Implement a bounded sync task using the existing account PATCH contract:
- anonymous language remains local-only;
- authenticated language change PATCHes `preferred_ui_language`;
- update `SESSION_QUERY_KEY` with the returned user;
- invalidate/refetch recommendations because explanation language depends on the server preference;
- define login/session reconciliation precedence deliberately:
  account preference should normally win for authenticated sessions unless an explicit product decision says otherwise;
- preserve the existing header location and morph animation;
- handle PATCH failure without trapping the UI in an inconsistent state.

No backend change is required.

## Medium

### M-01 — Idea sharing action is missing

Evidence:

- Source scope includes “save, share and comment on ideas”.
- Product overview says users can share an Idea.
- Roadmap Phase 9 lists “external share where supported”.
- No production frontend code uses `navigator.share`, clipboard copy, or another Idea-share control.

Impact:

Published Idea URLs are shareable manually, but the product has no actual share interaction.

Recommendation:

Add a lightweight progressive-enhancement Share action:
- use Web Share API when supported;
- fall back to copying the canonical Idea URL;
- provide accessible success/error feedback;
- no backend dependency or heavy library.

This is not a formal MVP blocker because the repository's MVP checklist does not enumerate Share.

### M-02 — Account/Profile is not yet a complete settings hub

Evidence:

- Frontend design maps Profile to “language/interests/settings/logout”.
- `/account` currently manages identity/avatar only.
- Interest settings and content-language settings exist and work:
  - `/onboarding/interests`
  - `/onboarding/languages`
- They are primarily linked from the authenticated Home page rather than grouped under Account/settings.
- Language toggle remains correctly in the header and should stay there.

Impact:

Settings exist but are fragmented. Users opening Account cannot discover all account preferences from that surface.

Recommendation:

Keep the header language toggle where it is, but add clear Account/settings links/cards for:
- Interests;
- Content languages.
Optionally expose the same links from the account dropdown if it remains uncluttered.

No new APIs are required.

### M-03 — No application-specific route/render error boundary

Evidence:

- Route pages are React.lazy-loaded and wrapped in Suspense.
- Suspense handles loading only.
- Router configuration has no custom `errorElement`, route error boundary, or app-level React error boundary.
- There is no localized recovery UI for:
  - lazy chunk import failure;
  - unexpected route render exception.

Impact:

Ordinary API failures are well handled, but unexpected render/chunk failures can fall through to generic framework behavior rather than an InsightInk recovery surface.

Recommendation:

Add a small localized route-level error boundary:
- retain/recover the persistent shell where practical;
- offer retry/reload/home actions;
- test a rejected lazy route and a render exception;
- keep dependency-free.

### M-04 — Repeatable E2E/accessibility/compatibility evidence is missing

Evidence:

- Testing strategy says Playwright should be introduced after real frontend/backend integration exists.
- Integration now exists.
- No project Playwright/E2E suite is present.
- WCAG 2.1 AA is the documented accessibility target.
- No axe/pa11y-style automated check is integrated.
- Compatibility matrix remains TBD; no recorded old iOS/Android/Firefox evidence exists.
- Manual Chromium/browser smoke reviews have been performed for several recent tasks, but they are not repeatable CI-style flows.

Impact:

Component/API coverage is strong, but final-project quality claims are not yet backed by reproducible browser/accessibility/compatibility evidence.

Recommendation:

Treat this as hardening rather than feature implementation:
1. add a very small critical-flow E2E suite;
2. add automated accessibility smoke checks for representative pages;
3. perform/document the compatibility matrix on available devices/browsers;
4. avoid claiming WCAG or old-device guarantees beyond measured evidence.

Dependency additions for Playwright/axe should be treated as a bounded hardening decision, not silently added during unrelated feature work.

## Low

### L-01 — Protected-route login return loses query/hash context

Evidence:

- `RequireAuth` and `RequireModerator` save only `location.pathname` into `state.from`.
- `LoginPage` navigates back to that string.
- Query parameters and hash are discarded.

Impact:

A deep protected URL such as a filtered moderation route can return to the route but lose its filter/query state after login.

Recommendation:

Store and restore `pathname + search + hash`, with tests.

### L-02 — Public Creator list backend capability has no direct frontend discovery surface

Evidence:

- Backend exposes public `GET /api/v1/creators/`.
- Frontend has no client for the creator-list endpoint and no creator-directory route.
- Creator profiles are still discoverable indirectly through Idea cards/detail and can be followed.

Impact:

Not a current MVP failure, but creator discovery depth is weaker than the backend capability and NFR language wording suggest.

Recommendation:

Do not prioritize above the High/Medium items. Consider a creator directory only if the product wants explicit creator browsing rather than Idea-led discovery.

## Confirmed complete / not a gap

### Topic browsing

Although `GET /topics/:slug/ideas/` has no direct frontend client, Search already provides topic browsing through the public search endpoint with a real Topic selector and shareable URL state. This satisfies the documented Explore “search/topics/formats” requirement without needing a duplicate page.

### Admin UI

No custom frontend admin panel is required by current architecture. Repository decisions explicitly use Django Admin for administrative/content-management duties. `can_administer` therefore does not by itself imply a missing React admin screen.

### Source traceability

Idea Detail displays source title, creator text, cover where available, and a real external original-source link. This satisfies the core source-inspection requirement.

### Onboarding continuity

Registration -> interests -> content languages -> app is implemented. Editing interests/languages later also works.

### Moderation

Report queue, report detail/actions, direct hide/restore, hidden-Idea list, permissions and audit-note behavior are implemented and tested.

## Deliberately deferred product requirements

These are documented second-wave/later milestones and are **not counted as current core-frontend defects**:

- realtime cross-device sync/WebSockets;
- direct messaging;
- notifications;
- TTS;
- membership/eBooks/payment;
- broader block/mute flows tied to messaging;
- privacy export/deletion flows that lack a backend contract;
- social sign-in, which remains an explicit open product question.

### PWA

Installable PWA is still required by NFR-10, but the roadmap explicitly places PWA/native-like complexity after the responsive web experience is stable. Current frontend has no manifest/service worker. PWA remains a planned required phase after core completeness and hardening.

## Audit conclusion

The frontend is not blocked and is already a strong working MVP, but it is **not yet complete enough to skip directly to visual polish/PWA**.

The two substantive product-consistency gaps are:
- missing Related Ideas;
- unsynchronized account UI-language preference.

Closing those first gives the cleanest transition into hardening, motion, and PWA.
