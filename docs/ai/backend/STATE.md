# Backend State

- BE-020 status: Complete; accepted by Backend Lead pending checkpoint commit/push.
- BE-020 base SHA: `94b766c176d3c90d6cdb6ae66018e094f6720310` (accepted/pushed BE-019 interests + deterministic recommendation checkpoint; clean starting worktree).
- Moderation domain: new `moderation` Django app owns reports, moderation audit actions, moderator-only queue/review APIs, and comment-report creation. The existing BE-013 Moderator/Admin authority model is reused rather than creating a second role system.
- Report model: `Report(reporter, target_type, target_id, reason, details, status, created_at, resolved_at)`. Generic target metadata supports the documented future target categories (comment/user/idea/message), but BE-020 publicly creates Comment reports only.
- Report reasons locked for current moderation baseline: `harassment`, `spam`, `inappropriate_content`, and `other`. `misinformation` is intentionally excluded because the security docs require a product policy before enabling that category.
- Report lifecycle is enforced as a state machine: `OPEN -> REVIEWING -> RESOLVED|REJECTED`. Reports cannot skip REVIEWING, terminal reports cannot be reopened/re-finalized, and resolved/rejected reports receive `resolved_at`.
- Public report endpoint: authenticated/CSRF-protected `POST /api/v1/comments/<id>/report/` accepts a bounded reason and optional details up to 2,000 characters. It only reports VISIBLE comments on PUBLISHED Ideas; hidden/deleted/non-public comments return 404.
- Moderation queue: Moderator or Admin only `GET /api/v1/moderation/reports/` with 25-item cursor pagination and optional validated `status` filter; `GET /api/v1/moderation/reports/<id>/` exposes report details, the reported Comment snapshot, and audit actions. Reporter/moderator summaries exclude email/account authority data.
- Moderation permissions: `IsModeratorOrAdmin` allows BE-013 bounded Moderators or Django superusers. Ordinary users and arbitrary `is_staff` users do not receive moderation access. Admin assignment of Moderator status remains BE-013-only.
- Moderation actions: authenticated role + CSRF-protected POST routes start review, hide the reported Comment, resolve the Report, or reject the Report. A Comment may be hidden only while its Report is REVIEWING; deleted/already-hidden comments cannot be hidden again.
- Content action semantics: moderator removal uses Comment status `HIDDEN`, not hard deletion. Public Comment reads already exclude HIDDEN/DELETED content, preserving evidence for moderation/audit instead of destroying it.
- Audit model: `ModerationAction(moderator, report?, action_type, target_type, target_id, note, created_at)` records review start, comment hide, report resolution, and report rejection. Actor, target, action, optional note, and timestamp are preserved. Notes are API-bounded to 2,000 characters.
- Audit/data retention baseline: Report reporter and ModerationAction moderator/report relations use PROTECT to avoid silently deleting moderation evidence. Final whole-account deletion/anonymization policy remains a documented later privacy decision.
- Generic target boundary: generic target storage is intentionally not a generic public API. Only Comment-report creation and Comment-hide action are currently exposed; user/idea/message targets remain reserved for later feature phases.
- Account restriction/block/mute boundary: no account restriction, block, or mute behavior is added in BE-020 because their final interaction semantics depend on later messaging/safety features.
- No casual moderator browsing: the moderation interface exposes target content through an existing Report detail; it does not add a free-standing moderator endpoint for browsing arbitrary private/deleted content.
