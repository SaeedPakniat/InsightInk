# Backend State

- BE-019 status: Complete; accepted by Backend Lead pending checkpoint commit/push.
- BE-019 base SHA: `c347442b3ea3c71e761bba95ca8088f5e51461d9` (accepted/pushed BE-018 bilingual Explore/Search checkpoint; clean starting worktree).
- Interest foundation: new `accounts.UserInterest(user, topic, created_at)` relation with PostgreSQL-backed unique constraint on `(user, topic)`. The conceptual optional explicit_weight is intentionally omitted from the baseline because no locked product contract uses weighted manual interests.
- Interest API: authenticated `GET /api/v1/me/interests/` returns the current user's active Topics; authenticated/CSRF-protected `PUT /api/v1/me/interests/` atomically replaces the entire explicit-interest set. Empty list clears interests; inactive/unknown/duplicate Topic IDs are rejected without replacing the valid existing set.
- Recommendation domain: new `recommendations` Django app owns selectors, pure scoring functions, deterministic explanations, orchestration services, API serializers/views/routes, and focused tests. It adds no recommendation cache/table.
- Personalized endpoint: authenticated `GET /api/v1/recommendations/` returns up to 20 ranked PUBLISHED Ideas. Each item contains the existing safe public Idea representation, a transparent numeric score, and one deterministic reason.
- Candidate strategy: recommendation scoring is performed over at most 200 recent-by-ID public candidates rather than loading the entire Idea table. Candidate visibility comes from the shared public Idea selector.
- Baseline scoring hypothesis: explicit interest match +5; capped saved-topic affinity up to +4; capped sparked-topic affinity up to +3; followed Creator +3; bounded Spark popularity 0..1; 30-day freshness 0..1. Save/Spark affinity caps after 3 interactions and popularity caps after 10 Sparks.
- Signal boundaries: preferred_ui_language is used only to localize explanation text, not as content-language preference. Language-fit remains 0 until a real content-language preference exists. Seen/read penalty remains 0 because Q-006 still lacks a definition of “read”; BE-019 does not fabricate consumption history.
- Recommendation explanations: reasons are derived from the strongest real scoring signal and support both Persian and English UI language. Examples include selected Topic, saved-topic affinity, sparked-topic affinity, followed Creator, popularity, and freshness.
- Related Ideas endpoint: anonymous/read-only `GET /api/v1/ideas/<id>/related/` returns up to 10 PUBLISHED topic-related Ideas. Jaccard topic similarity is the primary score; equal-similarity cross-format candidates receive a small diversity bonus, with tiny bounded popularity/freshness tie-break contributions. Unrelated and non-public Ideas are excluded.
- Related explanations: deterministic one-line reasons use the candidate Idea language, with Persian and English support, and identify shared Topic plus different-format diversification where applicable.
- Architecture: recommendation math lives in pure functions; selectors perform relational signal/candidate queries; services orchestrate; HTTP views remain thin. No LLM, RAG, embeddings, vector DB, agents, prompts, TF-IDF, or external recommendation service is introduced.
- Stored vs derived state: UserInterest is stored authoritative preference data. Recommendation scores/reasons are derived per request and are not persisted/cached until measured evidence justifies it.
- Migration: `accounts.0004_userinterest` creates only UserInterest and its unique constraint. Applied successfully to PostgreSQL; migration drift is clean. The recommendations app has no model migration.
